# ボロノイ分割による担当領域配分

`voronoi_partition_node` が、統合地図（`/map`, `icp_map_matching_node` が配信）と
各ロボットの現在位置から、ロボットごとの「担当領域マスク」を計算・配信する。
センサーベース探査・フロンティアベース探査の両方が、このマスクを目標選択の
制約として使う。

## 設計意図

新規性として構想している「ボロノイ分割によるICPマッチング精度と探査効率の
両立」のうち、**この実装が担うのは探査効率側（担当領域の重複排除）**である。
ICPの信頼度に基づくフロンティア選択（精度側）は、この分割の上に別途載せる
別コンポーネントとして構想しており、まだ未実装（設計は会話ログ参照）。

役割を分けている理由は次のとおり。

- ボロノイ分割は「どのロボットがどこを担当するか」という空間配分の問題であり、
  探査効率という単一目的で完結させたほうが設計として綺麗。
- ICP信頼度は「特定の候補地点に行ったとき、後でどれだけ良いマッチングが
  取れそうか」という局所的な予測値であり、領域全体を割る段階よりも、
  個々のフロンティア候補を比較する段階のほうが自然に扱える。
- 分割の役割と選択の役割を分けておくと、後で「探査効率への寄与」と
  「マッチング精度への寄与」を別々に評価実験できる。

## アルゴリズム

### 生成点

現在アクティブな全ロボットの位置。TF（`map -> <robot>/base_footprint`）から
毎サイクル取得するため、そのロボットが今センサーベース探査中かフロンティア
ベース探査中かに関係なく、常に生成点として扱われる。担当領域配分と探査モードは
直交する変数であり、モード切替のタイミングを全ロボットで揃える必要はない
（`explore_mode_monitor` によるロボットごと独立の切替をそのまま使ってよい）。

### 距離指標

単純なユークリッド距離ではなく、統合地図上の8近傍Dijkstra距離（直進 = 解像度、
斜め = 解像度×√2、障害物・未知セルは通行不可）を使う。壁の向こうが直線距離では
近くても、実際には遠回りになる状況を正しく扱うため。ロボットごとに1回、
計 N 回のDijkstraを実行し、各セルについて「最も近いロボット（所有者）」と
「2番目に近いロボット」の両方を記録する。

### 所有権が未確定のセル

どのロボットからも到達できないセル（例えば探査初期、2台のロボットが別々に
探査した地図断片がまだ統合地図上で繋がっていない場合）は、所有者を**割り当てない**
（`owner = -1`）。ロボットは行ったことのない場所を「自分の担当」と主張できない、
という考え方に基づく意図的な設計であり、フォールバックとしてユークリッド距離を
使うような代替処理は行っていない。

### 共有バッファ帯

境界を隙間なく分割すると、境界付近で両ロボットの探査済み領域が重ならなくなり、
ICPが対応点を取れる共通部分が無くなる。これを避けるため、最も近い所有者との
距離差が `buffer_width_m` 未満のセルは、両ロボットの「共有帯」として扱う
（マスク値 `50`）。既定値はICPノード（`icp_map_matching_node`）の
`overlap_filter_margin` の既定値 `2.0m` に揃えてある。

### マスクの値

`/<robot>/voronoi_mask`（`nav_msgs/OccupancyGrid`）のセル値:

| 値 | 意味 |
|---|---|
| `100` | このロボットの排他的な担当領域 |
| `50`  | 境界の共有バッファ帯（このロボット + 隣接ロボット） |
| `0`   | 他ロボットの排他的な担当領域 |
| `-1`  | 未確定（まだどのロボットも到達していない） |

## エスケープハッチ（空セル対応）

分割は生成点（ロボット位置）だけで決まるため、地図が育つ過程で「フロンティアも
未探査領域も一切残っていない」セルにロボットが配置されることが起こり得る
（中央寄りのロボットが周囲を他ロボットのセルに囲まれる状況など。ロボット2台でも
発生し得る）。

これに対しては、分割そのものを複雑にするのではなく、**消費側（探査ノード）に
2段階のフォールバックを持たせている**。

1. 自分の担当領域（`50`/`100`）内の候補だけで目標を探す。
2. 見つからなければ、その周期だけ担当領域の制約を無視して全体最良の候補を選ぶ
   （`frontier_explore_node::select_frontier_with_fallback`,
   `sensor_explore_node::control_loop` 内の2パスループ）。

`voronoi_partition_node` は `recompute_period_sec`（既定5秒）ごとに再計算する
ため、地図が育てば次のサイクルでそのロボットの担当領域にも新しいフロンティアが
現れる可能性が高く、恒久対応ではなく一時的な迂回として割り切っている。

## パラメータ

`launch/adaptive_explore.launch.py` の `VORONOI_PARAMS` で設定する。

| パラメータ | 既定値 | 説明 |
|---|---|---|
| `robot_names` | `ROBOTS` リストから自動生成 | 生成点として扱うロボット名 |
| `map_topic` | `/map` | 統合地図のトピック |
| `buffer_width_m` | `2.0` | 共有バッファ帯の幅 [m]。ICPの`overlap_filter_margin`と揃える |
| `recompute_period_sec` | `5.0` | 再計算の周期 [s] |
| `downsample_factor` | `2` | 計算前に地図を縮小する倍率（大規模ワールド対策） |
| `obstacle_threshold` | `50` | この値以上のセルを障害物として通行不可にする |

各探査ノード側の `use_voronoi_partition`（既定 `true`）で、ロボットごとに
Voronoi制約の有無を切り替えられる。ハイブリッド探査 vs
ハイブリッド+ボロノイ、という比較実験に使う想定。

## センサーベース探査での境界の扱い

現在は**ハード制約**（自セル外の候補を選択肢から完全に除外）を実装している。
反応的探査の即応性を損なう可能性があるため、境界に近づくほどコストが増える
ソフトペナルティへの変更も検討の余地がある
（`sensor_explore_node.cpp` の目標選択ループを参照）。
